奶茶 OCP 演示面板 用协议点一杯，不靠魔法

本页面只硬编码了一个地址：发现层 http://127.0.0.1:4500。 有哪些奶茶铺、它们的查询地址在哪、声明了哪些 query pack —— 全部由协议本身告诉页面。 这就是 OCP 存在的意义：跨独立目录发现。

1发现：谁在卖奶茶

先读 Registration 节点的发现文档，再读它的 manifest，最后按关键字检索已注册的 Catalog。 注意这三步都只跟发现层打交道，不涉及任何商品。

2选定一家，读它的 manifest

manifest 是 Catalog 的能力声明：端点在哪、声明了哪些 query pack 与过滤字段。 后续查询只能用它声明过的 pack。

3查询：按声明的 pack 检索商品

用 manifest 里宣告的 pack_id 查询。附带一个负例按钮：故意用一个未声明的 pack， 看节点是否会拒绝。

4解析：拿到点单入口（purpose=checkout）

对选中的条目做 resolve。协议在这里给出的是可执行入口，不是成交—— 每个下单绑定都标了 requires_user_confirmation。售罄商品拿不到下单入口，可以点下面的按钮试。

5下单：走商户侧的入口

这一步已经完全离开 OCP 协议面了——付款发生在商户侧。 本演示用 checkout_api 绑定直接 POST 一个 JSON 订单，观察返回单号。

协议层证据：node scripts/selfcheck.ts —— 34 个真实响应逐条过 JSON Schema（12 条官方 schema，22 条派生副本）。
行为证据：node scripts/probe.ts shanhai / node scripts/probe-registration.ts。
本演示不接任何支付通道：所有订单都带 payment: "simulated_not_charged"。
