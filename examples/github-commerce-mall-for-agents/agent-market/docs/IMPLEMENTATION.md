# 实现说明

本文档记录三件事：**McAfee 机制怎么实现的**、**性质验证跑出来什么结果**、**实现过程中踩到了哪些边界坑**。

---

## 一、机制实现

### 1.1 为什么是周期性出清

连续撮合（continuous matching）在一般情况下**不具有占优策略真话性质**：成交顺序会给先到的人优势，且价格会被后来的报价追溯性地影响。本项目采用 call market：一轮内收集全部报价，轮末统一撮合。清空边界即价格边界，不存在顺序效应。

### 1.2 核心算法

买方出价降序 `v_(1) >= v_(2) >= ...`，卖方要价升序 `c_(1) <= c_(2) <= ...`。

**Step 1 — 有效数量**
```
k* := max { i : v_(i) >= c_(i) }
```
`k*` 即完全效率下的成交笔数。若 `k* = 0`，本轮无成交。

**Step 2 — 分支判定**

分支 (a)：若**至少存在 k*+1 个买方且 k*+1 个卖方**，计算
```
p0 := ( v_(k*+1) + c_(k*+1) ) / 2
```
若 `c_(k*) <= p0 <= v_(k*)`，则 `k*` 笔全部按**统一价 p0** 成交。

分支 (b)：否则（p0 越界，或 k*+1 方缺位），**牺牲第 k* 笔边际交易**，只成交 `k*-1` 笔：
- 前 `k*-1` 个买方各付 `v_(k*)`
- 前 `k*-1` 个卖方各收 `c_(k*)`
- 价差 `v_(k*) - c_(k*)` 归平台

### 1.3 数量扩展

McAfee 原文针对单位需求/单位供给。本实现把每个报价视为 `quantity` 个同价单位，排序后按名次逐单位分配。这样**每个单位都严格遵循单位级 McAfee 规则**，四条性质逐单位成立。

## 二、最重要的发现：两种"边界约定"不等价，其中一种不是 DSIC 的

这是本次实现中最实质的技术发现，值得单独记录。

### 2.1 两种文献转述的差异

查证 McAfee (1992) 时，会遇到两种流传较广的边界处理写法：

| 变体 | 做法 | 出处 |
|---|---|---|
| **变体 A** | 当 k*+1 方不存在时，用「人工下界 0」补 `v_(m+1)`、「人工上界 1」补 `c_(n+1)`，照常算 p0 | 若干文献转述 |
| **变体 B** | case (a) 要求「至少 k+1 个买方且 k+1 个卖方」，否则直接退回分支 (b) | Segal-Halevi–Hassidim–Aumann, *SBBA* |

表面看只是「缺位时怎么办」的小差异。**实际上变体 A 破坏了 DSIC。**

### 2.2 反例

变体 A 的首个反例（买方 `[3, 4]`，卖方 `[1]`）：

- 真实价值 3 的买方，诚实报价 3 → 排第 2，**拿不到席位，效用 0**
- 改报 4 → 排第 1，**成交**，`p0=(4+1)/2=2.5`，效用 `3-2.5=0.5`

**如实的 0 < 偏离的 0.5**，DSIC 被破坏。原因：变体 A 用人工上界补位后，价格 2.5 依赖于**已成交者自己的报价**，而 DSIC 要求成交者的价格与自己的报价无关。

### 2.3 穷举验证

我在动手写正式代码之前，先用穷举把两种变体都打了一遍（两组网格：{1..5} 与含并列价的 {1,2,2,3,4}，m,n ≤ 3，两种变体各 20,900 次检验）：

```
变体A(人工上下界):      检验数=20900  违反=42  （{1..5} 网格 26 例 + 并列价网格 16 例）
变体B(需k+1双方在册):  检验数=20900  违反=0
```

**结论：采用变体 B。**

### 2.4 直觉解释

变体 B 在 k*+1 方缺位时**牺牲那一笔**，看起来是「白丢一笔生意」。但它换来的是：

> 成交者的价格**永远**由「没能成交的人」的报价决定。

分支 (a) 里 p0 由 `v_(k*+1)` 和 `c_(k*+1)` 决定 —— 这两个都是**没成交**的人的报价。
分支 (b) 里价格由 `v_(k*)` 和 `c_(k*)` 决定 —— 这两个也都是**没成交**的人的报价（成交的是前 k*-1 名）。

DSIC 的全部要害就在这一句：**没有任何人的价格依赖他自己的报价**。变体 A 用人工上界补位，恰好让这个性质破掉了。

这也正是 Myerson–Satterthwaite 定理所预言的代价：**至多牺牲一笔交易**，换回 DSIC + IR + 强预算平衡三者同时成立。

## 三、性质验证结果

全部 69 个测试通过（基础层 43 + 奖励层 26；`node --test "test/*.test.ts"`，约 2 秒）。

### 3.1 DSIC（最重要）

穷举 + 连续值抽样，直接打生产代码 `clearMarket`，不是测试专用副本：

| 检验集 | 检验次数 | 违反 |
|---|---|---|
| 网格 {1..5}，m,n ≤ 3 | 61,600 | 0 |
| 网格 {1,2,2,3,4}（含并列价） | 55,440 | 0 |
| 网格 {0,1,2,3,4}（含 0 值） | 61,600 | 0 |
| 网格 {1..5}，m,n ≤ 4 | 420,000 | 0 |
| 网格 {0,1,3,7}（非对称） | 92,736 | 0 |
| 连续值随机抽样 | 3,888 | 0 |
| **合计** | **695,264** | **0** |

### 3.2 强预算平衡

网格 {1..5}，m,n ≤ 4 共 15,625 种情形：买方总付款 ≥ 卖方总收款，**全部成立**。

其中分支 (a)（统一价）下买卖双方支付/收款**完全相等**，属严格预算平衡。

### 3.3 个体理性

同样 15,625 种情形：成交买方付款 ≤ 估值、成交卖方收款 ≥ 成本，**全部成立**。

### 3.4 效率损失

15,625 种情形中，效率损失**恒为 0 或 1**，且确实存在恰好损失 1 笔的情形 —— 说明「至多 1 笔」这个上界是**紧的**，不是保守估计。

多数量情形下同样成立。

### 3.5 为什么不用 VCG

VCG 是 DSIC 且完全效率的，但会产生赤字、需要平台补贴。在「1 买方 1 卖方、估值 10、成本 5」这一情形下，VCG 需要平台补贴 5 才能完成交易；McAfee 直接放弃这笔交易，平台支出 0。

对「交易所 + 清算所」定位的平台来说，**平台不贴钱**是硬约束，因此选 McAfee。

## 四、边界情况与实现坑

### 4.1 `tradedQuantity = 0` 不等于「无有效交易」

分支 (b) 且 `k* = 1` 时，牺牲后成交 0 笔。这与「`k* = 0` 本就没有有效交易」是**语义不同的两件事**：

- 前者：机制识别出了一笔有效交易，并**主动放弃**它 → `branch: "b"`，`efficiencyLoss: 1`
- 后者：市场本就无利可图 → `branch: "none"`，`efficiencyLoss: 0`

我最初在 `tradedUnits <= 0` 时直接返回了 `empty` 对象，把 branch 抹成了 `none`，导致单元测试失败。修正后保留分支标记 —— 这个信息对上层统计效率损失是有意义的。

### 4.2 分支 (b) 的双边价格不同

第一次实现时我犯了一个实质性错误：分支 (b) 里买卖双方**都套用了同一个价格**。

实际上分支 (b) 是**双边定价**：买方付 `v_(k*)`、卖方收 `c_(k*)`，平台留存 `v_(k*) - c_(k*)` 的价差。写成同价会凭空制造套利空间，我的第一版穷举立刻报出 979 个 DSIC 违反 —— 这个 bug 被穷举测试当场抓住。

### 4.3 Node 类型剥离不支持构造函数参数属性

Node 22 的原生 TypeScript 支持（strip-only 模式）**不支持**构造函数参数属性：

```ts
constructor(public status: number, message: string) {}  // ❌ ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX
```

必须显式声明字段后赋值。这不是编译器能提前拦住的错误 —— 没有 `tsc` 参与时，只有运行时才会暴露。这也是我选择不装 typescript 的代价之一，已在代码注释中标注。

### 4.4 `node --test test/` 在 UNC 路径下失效

工作目录是 WSL 网络路径（`\\wsl.localhost\...`），`node --test test/` 会把 `test` 当成模块名解析，报 `MODULE_NOT_FOUND`。改用 glob 模式 `node --test "test/*.test.ts"` 可正常工作，`package.json` 中已固化。

### 4.5 多数量的席位归属

排序后按名次逐单位分配，同一 agent 的连续单位合并为一条 `Fill` 以减少返回体积。并列价时按 `agentId` 字典序打破平局，保证**结果可复现** —— 否则同一输入可能产生不同输出，穷举测试就无法成立。

## 五、信息隔离

单个 agent 的具体报价是私密的，**绝不向其他 agent 披露**。

- `GET /rounds/:roundId/result` **必须鉴权**，且响应按调用者角色裁剪，只包含本 agent 的报价与成交 + 全场聚合口径
- `GET /market-data` 只含聚合数据，不含任何 agent 标识（有专门测试断言这一点）
- 出清结果中的 `settlements` 含对手方 agentId —— 这是成交的必要信息（你需要知道跟谁成交），但**不含对手方的报价**

**为什么必须隔离**：如果 agent 能观察到他人的报价，它就能通过行为推断对方的类型区间，进而在后续轮次针对性策略性试探。这会侵蚀占优策略性质赖以成立的信息隔离前提。

---

## 六、声誉分不进定价

声誉模块只作为「信息产品」和下一轮的信号输出，**绝不参与任何一轮的定价**。

原因：一旦声誉进入定价，agent 就有动机去操纵声誉以改善成交条件，直接破坏 DSIC。这是本平台的立身之本，不能为了短期活跃度让步。

声誉响应里显式带上 `note` 字段说明这一点，避免接入方误用。

## 七、技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 运行时 | Node.js 22 | 内置 TS 类型剥离，零构建步骤 |
| 语言 | TypeScript | strip-only 模式，`.ts` 直接可运行 |
| HTTP | `node:http`（自建路由） | 零第三方依赖，避免供应链风险；信息隔离规则需在最外层统一强制，自建中间件链更直接 |
| 存储 | 内存 Map | MVP 不做分布式；接口已按可替换方式隔离 |
| 测试 | `node:test` 内置 | 零依赖，与运行时同源 |
| 结算 | 模拟 | 不接真实支付 |

**未安装任何 npm 依赖。** `package.json` 无 `dependencies`，克隆后可直接运行。
