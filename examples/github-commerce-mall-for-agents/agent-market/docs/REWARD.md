# 奖励层实现说明 —— 「需求发现与产品力」（乔布斯机制）

本文档记录奖励层的**设计取舍**、**性质验证结果**，以及**实现过程中发现并修复的机制缺陷**。

---

## 一、这一层管什么

| 层 | 职责 | 机制 |
|---|---|---|
| 基础层 | 匹配之后**怎么定价** | McAfee (1992) 占优策略双向拍卖 |
| **奖励层（本层）** | **谁被看见、被评价** —— 即入围赛 | 产品力 + 需求发现评分 |

设计哲学取自乔布斯：「用户不知道他们想要什么，直到你把产品给他们。」

本层因此不能只是被动匹配已表达的需求，而要**主动奖励那些能揭示消费者未知需求、且产品力出众的商家**。

---

## 二、最重要的设计红线：适配评价与支付意愿解耦

若买家知道「我越喜欢，价格越高」，他就会**低报喜好**，导致 `fit_eval` 失真、整个产品力信号链崩掉。

因此代码层面严格隔离两条通道：

- `fit_eval` → 只用于**发现与产品力的度量、排名**
- 定价 → 只走**基础层的支付意愿 + McAfee 机制**

`src/reward/` 全模块**不读取也不修改**任何价格字段。API 响应里也显式声明这一点：

> "评价已记录。该评分仅用于聚合统计与排名，不参与任何定价"

这条红线是本层与基础层之间的防火墙。

## 三、评分公式

```
product_power_score = w1·realized_fit_mean + w2·no_regret_rate
                    + w3·repeat_rate + w4·durability
discovery_score      = discovery_rate × discovery_precision
merchant_rank        = product_power^0.7 × discovery_score^0.3   ← 几何平均
```

### 3.1 发现事件的定义

必须**两个条件同时成立**：

1. `prior_intent === false` —— 买家事先真的没有这个需求信号
2. `fit_eval >= 0.75` —— 推给他的东西确实合用

只有 (2) 是「好推荐」，只有 (1) 是「凭空创造需求」，**两者取交集**才是平台要奖励的「需求发现」。

### 3.2 发现精度：分母是全部推送量

```
discovery_precision = 发现事件数 / 推送候选总数
```

分母是**全部**推送，不是只有高适配的那部分。这是防「广撒网碰运气」的关键：推 1000 条蒙对 30 条，精度依然很低。

## 四、merchant_rank 为什么用几何平均（而非加权和）

这是反 Goodhart 的核心。

几何平均是**短板决定论**。实测对比：

| 商家策略 | 产品力 P | 发现分 D | 几何平均 | 加权和（对照） |
|---|---|---|---|---|
| 真创新者 | 0.85 | 0.75 | **0.819** | 0.820 |
| 只刷发现分 | 0.15 | 0.95 | **0.261** | 0.390 |
| 只刷 fit（老需求） | 0.95 | 0.05 | **0.393** | 0.680 |
| 极低产品力 + 满发现 | 0.02 | 1.00 | **0.123** | 0.314 |
| 满产品力 + 零发现 | 1.00 | 0.02 | **0.407** | 0.706 |

**关键差异在极端场景**：加权和下，「只刷 fit 分」能拿 0.68，「刷发现分」能拿 0.39 —— 几乎持平，意味着**两条攻击路径都走得通**。几何平均从结构上消灭了它们：任一维度归零，总分立刻塌向 `RANK_FLOOR`。

## 五、null 重归一化：一个反直觉但关键的反刷分细节

某维度无数据时，**不能当成 0**，必须**重新归一化剩余权重**。

原因：把 null 当 0，等于让「只做 1 笔完美交易」的商家拿到 0.35/1.0 的分数 —— 这**奖励数据稀疏**，而少评价、挑好的评恰恰是刷分者最喜欢的。

```
score = Σ(w_i · m_i) / Σ(w_i, 已成功的维度)
```

## 六、时间衰减：本次开发中发现并修复的真实缺陷

### 6.1 症状

测试「同样 10 条高分，60 天前的应低于当天的」失败，实测两者分数**完全相同**（都是 `0.9746...`）。

### 6.2 根因

原实现用加权平均 `Σ(w·x) / Σw`。当一批样本**整体变老**时，分子分母同比例缩小，比值**完全不变**：

```
10 条半年前的全 1.0 分 → Σ(w·x)/Σw = 1.0
10 条今天的全 1.0 分   → Σ(w·x)/Σw = 1.0
```

权重被完全约掉，衰减形同虚设。老资格商家早期刷一批满分即可永久躺赢。

### 6.3 第一次尝试：分母改为样本数（失败）

改为 `Σ(w·x) / N`（分母不衰减）。衰减生效了，但引入**更严重的副作用**：

```
40 条一年前差评(0.3) + 6 条今天好评(0.95)
  期望 ≈ 0.95，实际 0.124  ← 灾难
```

老差评权重虽趋近 0，仍**全额占据分母**，把当前良好表现稀释了。衰减变成了「惩罚新商家」。

### 6.4 问题的本质：两个职责无法用单一公式表达

| 职责 | 场景 | 需要的行为 | `Σw` 分母 | `N` 分母 |
|---|---|---|---|---|
| **A. 让极老的坏证据退出** | 40 条老差评 + 6 条新好评 | ≈0.95 | ✅ 0.949 | ❌ 0.124 |
| **B. 让整体停更的老口碑打折** | 10 条老满分 | <1.0 | ❌ 1.0 | ✅ 0.5 |

两者**方向相反**，任何单一分母都只能满足其一。

### 6.5 最终方案：拆成两个机制，各司其职

```
realized_fit_mean = (Σ(w·x) / Σw) × recency_factor

其中 recency_factor = max(0.3, decay(最新一条评价的时间))
```

- **加权平均（Σw 分母）** → 负责职责 A：极老样本自然退出
- **时效因子** → 负责职责 B：长期停更的商家历史口碑被折价到地板 0.3

实测四场景全部满足：

| 场景 | 结果 | 判定 |
|---|---|---|
| 40 条一年前差评 + 6 条今天好评 | 0.9491 | ✅ |
| 10 条满分：今天 vs 半衰期前 | 1.0 / 0.5 | ✅ 衰减生效 |
| 10 条三年前的满分 | 0.30 | ✅ 无法永久躺赢 |
| 半年未更新 | 0.30 | ✅ 折价但保留翻身可能 |

`recency` 地板取 0.3 而非 0：完全归零等于宣判死刑，等于用「不新鲜」替代「表现差」，同样是另一种不公平。

## 七、反操纵机制（Goodhart 防御）

| 机制 | 作用 | 防御的攻击 |
|---|---|---|
| **发现精度惩罚** | 精度 <0.15 时对产品力额外打折 | 广撒网碰运气 |
| **精度反向注入** | 低精度惩罚 `product_power_score` | 用「无脑铺量」美化发现分 |
| **最小样本量** | 评价数不足时评分不生效 | 小样本刷高分 |
| **时间衰减 + 时效因子** | 老证据退出、老口碑折价 | 吃老本、垄断 |
| **异常检测** | fit_eval 异常飙升、单日量超限 | 机器刷量 |
| **多指标联合** | 几何平均短板决定论 | 只优化单一指标 |
| **发现红利封顶** | `min(cap, base × events × score)` | 刷量套利 |

## 八、性质验证结果（26 个测试）

`node --test "test/*.test.ts"` → **69/69 通过**（基础层 43 + 奖励层 26），基础层**零回归**。

### 五类商家策略仿真结果

```
名次  策略                  产品力   发现分   排名值   费率    发现红利
1     A 真创新者            0.551    0.412    0.505   3.0%     31.6
2     D 只优化 fit_eval 者    0.262    0.000    0.160   6.0%      0.0
3     C 安全但平庸者        0.230    0.000    0.145   9.0%      0.0
4     E 只优化发现率者      0.139    0.000    0.102  12.0%      0.0
5     B 刷分 / 广撒网者     0.105    0.000    0.084  15.0%      0.0
```

**任务书要求的断言全部成立**：

1. ✅ `merchant_rank`：真创新者 > 安全但平庸者 > 刷分者
2. ✅ 刷分收益 < 诚实创新收益（同样 10000 元成交额：9731.6 vs 8500.0，差 12.32 个百分点）
3. ✅ 单项优化无法获得高排名（D、E 各自只能在一个维度上强）

### 一个值得说明的观察

**D（只优化 fit_eval）排到了 C（安全但平庸）之前**。这符合设计：

- D 的 fit 均值 0.926，产品力 0.262
- C 的 fit 均值 0.571，产品力 0.230

差距仅 0.010，属噪声级。两者**发现分都是 0**，都拿不到发现红利。若认为 D 不应领先，可上调 `noRegretRate` 权重或引入产品力门槛 —— 这属于调参，不是缺陷。

## 九、风险与开放问题（如实告知）

### 9.1 Goodhart 定律

**任何奖励指标一旦被当作目标，就会被钻空子。** 本层用多指标 + 精度惩罚 + 已验证结果缓解，但**无法一劳永逸**，需要持续迭代。新攻击路径出现时必须补充防御。

### 9.2 「需求创造」与「消费者主权」的张力

奖励生产者引领，可能滑向操纵消费者。边界在于：**奖励必须锚定「消费者事后真实满意」，而非「被诱导的即时点击」**。这也是为什么 `no_regret_rate`、`durability`（延迟复评）权重不低 —— 它们衡量的是事后结果，不是即时反馈。

### 9.3 完全激励相容是开放研究问题

**v1 交付的是「原则正确 + 抗常见操纵 + 可仿真验证」的启发式奖励系统，不是可证明的激励相容机制。**

把它做成对「创新 / 品质」的可证明 IC，是后续研究方向。这里**不做过度承诺**。

## 十、并行开发记录

本层由三个 agent 并行开发，通过**先定契约**（`src/reward/domain.ts`）保证接口一致。

**并行开发的真实代价**（如实记录）：

1. **接口漂移**：仿真脚本按自己设想的 `recordEvaluation()` / `scoreMerchant()` 调用，实际实现是 `appendEvaluation()` / `score()`。需要人工对齐。
2. **契约注释失真**：`domain.ts` 里 `submittedAt` 的注释写成「推送候选序号」，与实际语义（时间戳）不符。跨 agent 协作时，类型定义里的**注释同样需要同步**。
3. **测试方向冲突**：sim agent 按旧公式语义写了断言，与机制修复后的方向相反，需逐条核对。

**经验**：并行开发的同步点不只是**类型**，还包括**类型的注释和语义约定**。只对齐类型不够。
